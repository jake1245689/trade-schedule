# AI Landscape Render Studio

Upload a photo of a yard, then describe changes in plain English — plants, paving,
placement, brick features, lighting — and get back an AI-edited render. Projects and
render history are saved per account.

This is built to run for **$0**: no paid AI API keys, no paid hosting required.

## How the "free" AI part works

Image edits are generated by [Pollinations.ai](https://pollinations.ai)'s `kontext`
model, which is free and requires no signup or API key. It works by fetching your
photo from a public URL and applying your text prompt to it. That's why this app
needs a real backend (to host the uploaded photo at a URL Pollinations can fetch) —
a client-only site can't do this.

**Limits of the free tier** (from Pollinations' own docs):
- Anonymous use is rate-limited to roughly **1 request every 15 seconds**.
- Free-tier images may carry a small watermark; a free account at
  [auth.pollinations.ai](https://auth.pollinations.ai) removes it and raises limits
  (optional — not required to use this app).
- It's a third-party free service with no uptime guarantee. If it's ever slow or
  down, generation will fail with a clear error message asking you to retry — nothing
  else in the app breaks.

## Project layout

```
ai-landscape-render/
  server/   Express API + SQLite database + serves the built frontend
  client/   React (Vite) frontend
```

Everything runs as a **single Node process** in production: the Express server
serves the built React app plus the `/api` and `/uploads` routes.

## Running it locally

Requires Node.js 18+.

```bash
# 1. Install dependencies
cd server && npm install
cd ../client && npm install

# 2. Configure the server
cd ../server
cp .env.example .env
# Edit .env and set JWT_SECRET to a long random string, e.g.:
#   node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"

# 3. Start the backend (http://localhost:3001)
npm run dev

# 4. In a second terminal, start the frontend dev server (http://localhost:5173)
cd ../client
npm run dev
```

Open http://localhost:5173, create an account, and create a project.

> **Note on testing generation locally:** Pollinations fetches your uploaded photo
> from a URL it can reach over the public internet. `localhost` isn't reachable from
> the outside, so image generation won't work from a purely local dev setup unless
> you expose your local server with a free tunnel, e.g.
> [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/get-started/)
> (`cloudflared tunnel --url http://localhost:3001`) or `ngrok http 3001`, and set
> your browser to hit that tunnel URL. Once deployed to any real host (see below),
> generation works normally with no extra steps.

## Running it as one process (production-style)

```bash
cd client && npm run build      # outputs client/dist
cd ../server && npm install --omit=dev
JWT_SECRET=<your-secret> COOKIE_SECURE=true npm start
```

The server serves the built client automatically from `client/dist`.

## Deploying for free

Any host that runs a persistent Node.js process works. A few genuinely free options:

- **A spare computer / home server / Raspberry Pi**: run the "one process" command
  above and use a free dynamic-DNS or Cloudflare Tunnel to get a public URL. This is
  the most reliable free option since your uploads and database live on disk you
  control and nothing gets wiped.
- **Fly.io free allowance**: supports small persistent volumes, so your SQLite
  database and uploaded images survive restarts. Mount a volume at
  `ai-landscape-render/server/data` and `ai-landscape-render/server/uploads`.
- **Render.com free web service**: easiest to set up, but its free tier's disk is
  **ephemeral** — uploaded photos and render history will be lost whenever the
  service restarts or redeploys. Fine for a quick demo, not for long-term history.

Whichever host you use, set these environment variables:
- `JWT_SECRET` — a long random string (sessions are invalidated if this changes).
- `COOKIE_SECURE=true` — once the site is served over HTTPS (required for login
  cookies to work correctly in production).

## Data model

- **Users** — email + bcrypt-hashed password, JWT session cookie.
- **Projects** — a name + the original uploaded photo.
- **Renders** — belong to a project; each has the prompt used, which image it was
  generated from (the original photo, or a previous render — so you can layer
  changes, e.g. add paving first, then add plants on top of that result), the
  resulting image, and its status (`pending` / `done` / `error`).

## Security notes

- Passwords are hashed with bcrypt; sessions use httpOnly, signed JWT cookies.
- Uploads are restricted to JPEG/PNG/WEBP, capped at 15MB, and stored under
  server-generated random filenames.
- All project/render routes check that the resource belongs to the signed-in user.
